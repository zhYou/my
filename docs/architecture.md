# my 架构说明

本文记录已确定的项目边界和后续模块设计依据。当前已实现能力与开发操作以根目录 [README](../README.md) 为准。

## 定位与当前阶段

`my` 是个人数据与资源管理 CLI，面向机器、配置文件、私有账号、云厂商和云服务。
公开代码仓的模块路径为 `github.com/zhYou/my`，命令名为 `my`。

当前只完成工程基础：模板初始化、命令发现、严格配置、双语消息、诊断、测试及构建发布流程。
`greet` 保留为验收示例，产品 CLI 的 `doctor` 是空检查入口。
下面的业务模型与数据访问方式属于后续设计方向，尚未接入任何真实机器、数据仓或云账号。

## 数据与凭据

| 层次           | 职责                                            | 边界                                                  |
| -------------- | ----------------------------------------------- | ----------------------------------------------------- |
| 公开代码仓     | CLI、适配器、校验规则、测试、文档和脱敏示例     | 不保存真实个人数据、账号资料、凭据或生产配置          |
| 私有数据仓     | 机器与资源记录、关联关系、配置期望值及 age 密文 | 敏感账号资料、密码、token、私钥和私密文件只以密文保存 |
| 仓外凭据       | 唯一 age 解密凭据及数据仓访问认证               | 用户自行保管；不自动生成、提交或复制到示例            |
| 本机状态与缓存 | 同步基线、实际状态摘要、恢复记录和诊断          | 应用私有目录；秘密不以明文进入日志、缓存或状态        |

私有数据仓的访问认证和 age 解密凭据必须能在首次读取数据仓之前取得，避免把首次访问所需凭据只存于待访问的数据中。
本次初始化不创建私有数据仓，也不读取、加密、解密或迁移任何真实数据。

应用必须从文件读取的私密配置，后续由文件适配器写入明确声明的目标，使用受限权限。
将秘密写入目标配置文件的能力，与对 shell、Windows 用户环境或 macOS GUI 注入应用环境变量的能力分开；后者不在本项目范围内。

## 业务模块

业务模块按实际需求逐个实现，新增目录以可运行功能为依据。

| 领域   | 管理对象与职责                                               |
| ------ | ------------------------------------------------------------ |
| 机器   | 机器登记、平台与用途描述、机器与资源的关联                   |
| 配置   | 完整文件和结构化字段的管理、机器差异、校验、变更计划与同步   |
| 账号   | 私有账号资料、用途及其与云厂商、云服务的关联                 |
| 云服务 | 厂商、账号下的服务与资源记录，以及按需增加的查询或操作适配器 |

资料的登记查询与外部资源的创建、变更、销毁具有不同的执行边界。
具体云资源操作、WireGuard 支持、秘密编辑入口和旧数据迁移，都在相应模块实施前单独设计，不因存在记录而自动获得执行能力。

## GitOps 与同步

配置管理采用声明式期望状态和版本追踪；机器、账号及服务资料采用版本化记录。
[OpenGitOps 原则](https://opengitops.dev/#gitops-principles)还包括自动拉取与持续收敛，
本阶段仅建立前两项的设计基础，业务实施后先由 CLI 手动触发检查和同步。

远端数据通过 GitHub API 适配器访问，私有 Git 仓库保存版本历史；本机保留必要同步状态与缓存，不维护完整 Git 工作树。
通过 API 访问不会自动消除并发冲突，后续同步协议必须处理远端版本变化、断网和中断恢复。
具体 API、提交方式与双向变更规则在配置模块实施前单独确定。

配置文件按结构和字段归属管理：

- 声明纳管字段及适用机器，使用 Schema 或有类型模型校验结构和取值。
- 保留应用自行维护、未纳管及本机专属字段，避免整份文件相互覆盖。
- 由文件格式适配器完成读取、精确修改和输出校验；不能可靠解析的内容不得按猜测写入。
- 本地基线用于区分已同步状态与后续变更；同一字段的真实并发修改需要明确的处理规则。

Schema 校验、字段归属和同步策略是不同的职责；仅通过 Schema 校验不足以决定一项改动应上传、下发或保留在本机。

## 代码组织与工具

沿用 starter 的职责边界：程序入口处理信号与退出，CLI 处理参数和呈现，应用层组合业务与资源，
公共机制位于 base，外部进程通过统一 command 能力调用。详细约束见[设计指南](design-guidelines.md)。
本次不增加空业务包、通用插件框架、云厂商 SDK 或数据存储协议。

后续文件与资源收敛由 Go 实现，不引入 chezmoi 运行时依赖。
业务不包含软件升级、Topgrade 或应用环境变量注入；mise 继续负责开发工具链。
是否增加新设备的工具安装能力，留到机器模块设计时决定，本次不移植旧工作流。

CLI 自身继续使用模板的 TOML 配置、`MY_HOME`、语言及诊断环境变量。
这些变量控制本程序的运行，与向其他应用投影环境变量无关。

## 验证与演进

各模块实现时同时维护命令 Schema、类型、帮助、双语消息、文档和测试。
读取真实数据前先通过脱敏 fixture、隔离 HOME 和受控远端替身验收；涉及平台行为时增加对应平台原生验证。
跨平台构建不替代目标设备运行时验收。

旧 `machine-config` 仅作为历史能力和回归场景的参考，不自动迁入其数据、状态、命令兼容层或 Git 历史。
当前不提供旧项目的替换或迁移入口。
